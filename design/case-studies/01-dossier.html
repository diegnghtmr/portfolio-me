Problem & context

Brújula was scoped to one university. The boundaries between curriculum, progress and simulation were still being worked out when the architecture was chosen.

Students declare their own academic data rather than using official institutional records. Staff see aggregate information, not individual grades.

Architecture

The backend owns the OpenAPI contract. The frontend tracks a copy of that contract and uses an Axios client generated from it.

Decisions

The records describe the team’s choices. Diego’s individual involvement: To confirm.

One deployable backend

Options
Independent microservices or a modular monolith.
Choice
Use Spring Modulith in one Spring Boot process.
Consequence
Less distributed-system overhead up front, but all modules share one JVM and deployment lifecycle.

single Spring Boot process

ADR-001: Modular monolith ↗

One authoritative API contract

Options
A hand-written contract, contract validation only, or a generated server and client.
Choice
Use OpenAPI contract-first and treat the backend contract as authoritative.
Consequence
Generation reduces the risk of drift, but the frontend copy has to stay in sync and the client has to be regenerated.

authoritative

ADR-006: OpenAPI contract-first ↗

Aggregate-only staff access

Options
Let staff access individual grades or show aggregates only.
Choice
Show only aggregates to staff in the MVP.
Consequence
Helping an individual student would require a delegate-access feature later.

no access to individual student grades
