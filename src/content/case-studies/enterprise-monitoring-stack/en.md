## Problem

In a University of Quindío infrastructure lab, three services that had been hosted on separate physical servers were brought onto one machine. Consolidation raised two questions: which data should survive when an individual service is replaced, and how can an operator tell which service is active when they all draw on the same resources?

The team had to keep the two web roots and the database files separate from the containers that use them. A web page or SQL connection could confirm that each service answered, but not show what happened between checks. The lab therefore paired service deployment with persistent storage and a dashboard for observing the shared machine and its containers.

## How it works

The repository contains the deployment reference and the lab walkthrough; there is no separate application repository. Apache and Nginx serve independent web roots, while MySQL maintains its own database directory. Compose describes a container for each service and a fourth for Netdata. It does not connect the web servers to MySQL as part of an application.

In the documented VirtualBox setup, nine virtual data disks form three RAID 1 arrays. Each array backs one LVM volume group and one logical volume. The volumes are formatted as ext4, mounted under `/srv`, and bind-mounted into the appropriate container. This keeps web content and database files outside the containers’ writable layers. The guide checks persistence by restarting or replacing service containers.

The documented Netdata agent collects host and container metrics. For the local captures, the three checked-in Dockerfiles were built with missing fixture files supplied locally. Named Docker volumes stood in for the guest mounts. Netdata read Apache’s status endpoint, Nginx connection counters, and MySQL status variables over the Compose network, without mounting host files or the Docker socket. Those charts show traffic and queries from the local workload; they do not show a disk failure or recovery.
